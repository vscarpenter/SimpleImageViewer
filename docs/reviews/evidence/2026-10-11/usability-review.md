## Verdict

The existing Studio layout and recently redesigned native Settings are a useful base. The highest-value work is to finish keyboard and accessibility behavior, restore commands that disappear in Single view, remove the mismatch between Settings and rendered behavior, and fix window-delegate ownership. A new material treatment should follow those changes. The subfolder feature will benefit from a scope control and native folder list rather than another folder-selection screen.

These are behavior changes, not an aesthetic redesign. Existing Settings brief/tokens remain authoritative. Review used the UI Craft accessibility floor and evidence gate, and Build macOS Apps scene/commands/split/inspector guidance.

## Sound decisions to preserve

- Settings uses a retained native AppKit preferences window/controller, system preference toolbar, grouped forms, standard switches/stepper, NSSearchField, and no custom pane animation. Its implementation follows the approved compact native Settings direction.
- Inspector Insights uses native buttons/disclosures, selection-enabled descriptions/OCR, accessible section headings, stable labels, copy success announcements, cancel/refresh states, and visible specific caveats before collapsed optional sections. The prior result remains available during refresh.
- Keyboard capture correctly rejects events from other windows, sheets, text editors, and focused controls using both native and SwiftUI focus signals. Do not replace that policy with unconditional global hotkeys.
- Grid and filmstrip are lazy containers, use downsampled first-frame thumbnails, retain stable image identity, and honor Reduce Motion during selection scrolling. The viewport disables precision-gesture animations deliberately.
- Trash captures image/folder identity, confirms deletion, prevents repeated actions, and preserves a newer selection while the operation finishes. This review did not identify an unconfirmed destructive-action flow.
- Stage and inspector have distinct roles; numeric counts/zoom values already use monospaced digits. Preserve that content-first hierarchy.

## macOS 27 optimization direction

1. **Adopt system window chrome incrementally.** The current 52pt HStack toolbar reserves a hardcoded 78pt traffic-light inset and implements its own overflow menu. A native macOS `.toolbar` with logical groups and customization would supply system placement/overflow and appearance adaptation, while keeping folder/scope, Single/Strip/Grid, zoom/density, and inspector actions. This is a proposed design/architecture improvement, not a claimed compatibility failure. Apple recommends letting the system manage overflow and reducing custom toolbar backgrounds. Use macOS-supported item visibility/priority and native overflow; the `toolbarOverflowMenu` SwiftUI modifier is unavailable on macOS, so do not use it here. [Apple Toolbars guidance](https://developer.apple.com/design/human-interface-guidelines/toolbars?changes=_2).
2. **Use a resizable native inspector.** Current [InspectorView.swift:27](/Users/vinnycarpenter/Projects/SimpleImageViewer/StillView%20-%20Simple%20Image%20Viewer/Views/InspectorView.swift:27) fixes width at 300pt. A native `.inspector` with roughly 280–440pt width bounds would let long descriptions and metadata breathe and help fit a future folder sidebar. Retain Info/Insights tabs and the pinned action footer. [SwiftUI inspectorColumnWidth](https://developer.apple.com/documentation/swiftui/view/inspectorcolumnwidth(min:ideal:max:)).
3. **Make window intent explicit.** The app creates a WindowGroup but keeps one global mainWindow and WindowStateManager, posts unscoped folder notifications, and finds windows with `NSApp.windows.first`. Decide whether browsing supports one workspace or independent workspaces; route commands through scene focus either way. Do not market multiple-window browsing until selection/restoration is scene-scoped. [Apple menu-bar scene focus guidance](https://developer.apple.com/documentation/swiftui/building-and-customizing-the-menu-bar-with-swiftui).
4. **Connect generated description to image accessibility.** Main image accessibility currently exposes only filename and zoom. After a successful analysis, offer the concise description as the image’s accessible description while preserving filename/zoom separately and keeping analysis optional. The same description could support an explicit copy-as-alt-text workflow later, but that expands the approved Insights scope and should be designed separately.
5. **Keep new materials out of image pixels.** Let native chrome adopt the current system appearance; retain an opaque, stable stage for evaluating images. The approved Settings brief favors native system treatment and no decorative motion; there is no reason to add more blur or animation to that surface.

## Subfolder browsing implications

The new capability should make scope visible. Place “This folder / Include subfolders” beside the selected folder and show total images plus a discovery/loading state. “All images” should aggregate descendants, while an optional native source-list sidebar lets a person inspect an individual child folder without reopening the picker. It must be clear whether counts include descendants.

Mixed-folder results need identity beyond the basename: selected-image Info should expose relative folder/path, and grid hover/accessibility labels should distinguish two `IMG_0001.jpg` files. Preserve an optional caption rather than introducing dense metadata on every tile. Keep sort and filter meaning consistent across the aggregate and individual-folder views. At the current 800pt minimum, adding a sidebar to the fixed 300pt inspector leaves a cramped stage; native collapsible sidebar/inspector behavior should be part of that feature design.

## Remaining checks and deliberately excluded candidates

- **VoiceOver:** verify grid activation/selection announcements and recent-folder rows in the actual accessibility tree; source-only absence of an explicit accessibilityAction is not proof that SwiftUI synthesizes none. Notification message visibility was falsified as a defect: [ContentView.swift:207](/Users/vinnycarpenter/Projects/SimpleImageViewer/StillView%20-%20Simple%20Image%20Viewer/App/ContentView.swift:207) combines children and sets a parent label containing the complete severity and message. Lack of a live announcement remains an untested candidate, not a confirmed inaccessible-message finding.
- **Keyboard focus:** tab into/out of grid, filmstrip, toolbar, inspector and disclosure groups; verify clear ownership after clicking a native control. RecentFolderRow uses tap gestures with named accessibility actions but no keyboard-focus support; test whether keyboard-only opening of recent folders works at the cold-start screen.
- **Modal overlays:** ErrorHandlingService’s critical errors and permission prompts are custom ZStack overlays, without explicit initial focus, focus containment, or dialog semantics. Native folder-opening errors already use `.alert`. This remains a candidate until a reachable critical-error/permission case is triggered and tested.
- **Increase Contrast / Reduce Transparency:** viewer tokens resolve only light/dark custom colors while Settings uses system controls. Test rendered controls, separators, selection rings and small metadata text with actual accessibility appearance settings before assigning a numerical contrast defect.
- **Enhancements:** the live automatic-enhancement preference describes color, noise and cropping changes, yet the viewer has no visible “enhanced” indication or Original/Enhanced control. Verify the actual active processing path and distinguish its displayed pixels from the original pixels used for Insights before designing a comparison affordance; AI/performance reviewers own that deeper analysis.
- **Animation:** the stage arrows animate opacity; opacity-only transitions are allowed by UI Craft’s reduced-motion guidance. No finding is assigned merely because those arrows lack a Reduce Motion branch.
- **Styling:** gradient-heavy folder landing cards, 8.5pt exposure labels, and old glass-effect helpers were noticed. They were not promoted to primary findings because behavior/accessibility matters first, some helpers are not on the current render path, and no screen measurements were performed by this reviewer.
